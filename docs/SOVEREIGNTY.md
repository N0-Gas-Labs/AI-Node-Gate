# Sovereignty

## What sovereignty means here

Sovereignty is not a feature you switch on. It is a set of properties that determine whether a system is something you *own* or something you *rent*. A rented system works exactly as long as someone else's business, pricing, and policy allow it to, and it can be changed, rate-limited, or switched off without your consent. An owned system runs on hardware you control, holds data you can read, and can be proven honest without asking anyone's permission.

AI-Node-Gate is built to be owned. This document sets out the four kinds of sovereignty the hub pursues, how each is implemented in this repository, and — honestly — where the current build stops short.

## 1. Runtime sovereignty — no dependencies

The hub runs on the Python standard library and nothing else. There is no framework to install, no package registry to trust, no lockfile that rots, and no vendor that can deprecate the ground you stand on. A machine with Python and a copy of this repository *is* the hub. This is a deliberate trade: we give up the convenience of third-party libraries in exchange for a system that cannot be broken by someone else's decision.

Concretely, the hub uses `http.server` for its runtime, `sqlite3` for storage, and a self-contained `ed25519` implementation for cryptography. Every one of those is in the standard library or in this repository. You can read the whole thing.

## 2. Data sovereignty — one file you hold

The entire hub lives in a single SQLite file, `.ngg/hub.db`, next to a keyring file, `.ngg/keyring.json`. There is no cloud account, no sync service, and no hidden state. Copy the file and you have copied the hub; move it to another machine and it keeps working. The schema is plain enough to inspect with any SQLite tool, or even by eye.

Beyond the working database, the hub can export a **sovereign bundle**: one JSON file containing every node, proposal, decision, and ledger entry, plus a manifest hash over the public record. The bundle is the hub in a form that can be archived, moved, or handed to someone else — and verified by them without trusting you.

## 3. Identity sovereignty — keys, not accounts

There are no usernames and passwords, and no identity provider. Every actor has an Ed25519 keypair generated locally. Each node signs its own proposals; the human arbitrator signs every decision. The hub verifies signatures against public keys, which means it can prove who did what *without holding the private key that proves it*.

The private keys live in the keyring file, which the operator owns and which is written with `0600` permissions. In this single-operator build the hub signs on the operator's behalf for convenience. The architecture keeps signing and verification strictly separate, so a hardened deployment can move signing onto the operator's own device — a hardware token, an air-gapped machine — without changing the record format at all. That separation is the important part; where the key physically sits is a deployment choice.

## 4. Compute sovereignty — your models, your hardware

A node is only as sovereign as the model behind it. If every proposal is drafted by a rented API, the hub is sovereign in name only. The hub therefore speaks to a **local model runtime** over a plain HTTP endpoint, using the widely-supported Ollama / llama.cpp-server request shape. Point it at Ollama, llama.cpp's server, LocalAI, or LM Studio running on your own machine, and your nodes draft with a model on hardware you control.

If no local runtime is reachable, the hub falls back to a deterministic drafter so the system is always demonstrable. The fallback is a convenience, not the design. The default is your own machine.

## 5. The verifiable record — proof, not promises

The ledger is an append-only hash chain. Each entry commits to the hash of the entry before it, so altering or removing any entry breaks every hash after it. Verification is a pure function of the record itself: anyone with the ledger can recompute the chain and confirm it was not tampered with. The same is true of every signature — a proposal or decision can be verified from the public keys alone, offline, with no access to the hub.

This is what turns "trust me" into "check for yourself." A sovereign system does not ask to be believed. It hands you the evidence and the means to test it.

## Where this build stops short — honestly

Sovereignty is a direction, not a destination, and this build is early. Three honest caveats:

- **The operator's key is held by the hub.** Convenient for one person running one hub, but it means the hub process can sign as the operator. Moving signing to the operator's device is the single most important hardening step, and the architecture is already shaped for it.
- **Node keys are generated by the hub.** The hub mints a keypair per node and keeps the secret, which is fine for a local agent runtime but not for nodes that are genuinely independent parties. Independent nodes should generate their own keys and hand over only their public key.
- **The record is verifiable, not yet replicated.** A hash chain proves integrity; it does not, by itself, prove availability. Durable, replicated storage — so that the record survives the loss of any one machine — is a later phase.

Naming these limits is part of the point. A sovereignty claim that hides its gaps is not sovereignty; it is marketing.

## The principle, in one line

Autonomy for the nodes, authority for the human, and a record that anyone can verify — running on hardware you own, with nothing rented and nothing hidden.
